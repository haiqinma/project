# Project 文档目录规划

本文档定义 Project 仓库后续文档的目录结构、命名规则、归档规则和维护流程。目标不是立刻整理现有 `docs/` 下的历史文档，而是先建立后续新增和迁移文档的落位标准，避免设计、协议、运维、历史背景和生成物继续混在一起。

## 规划目标

- 让新文档可以快速判断应该放在哪个目录。
- 让当前有效文档、历史背景文档、生成式文档有明确边界。
- 让 Project、Node、Agent、Wallet、OnlyOffice 等跨系统文档能按职责组织。
- 让后续迁移现有文档时有稳定规则，不依赖临时判断。
- 让 README 始终作为导航入口，而不是承载过多正文内容。

## 总体结构

后续建议将 `docs/` 逐步收敛为以下结构。目录和文件名统一使用中文；英文仅用于协议版本、命令名、代码标识和外部产品名称：

这是目标结构，不要求一次性迁移。初期只建立实际需要的顶层目录；某个主题达到 3～5 篇文档，或形成多个稳定子主题后，再建立对应的二级目录。新文档优先按这套结构创建；老文档只在被实质修改、合并或废弃时顺手迁移。

目录按“文档用途”分类，外部系统名称只作为二级目录或文档名，不再建立另一套平行分类。每篇文档只能有一个主归属目录，跨领域内容通过链接引用，不复制正文。

## 目录职责

### 根目录

`docs/README.md` 是文档总入口，只保留导航、当前推荐阅读路径和少量维护说明。它不承载详细设计正文，也不作为临时草稿堆放位置。

`docs/文档目录规划.md` 是本文档，负责说明文档系统怎么组织、怎么命名、怎么演进。

### 架构

放系统级和领域级架构文档，回答“系统是什么、边界在哪里、核心模型如何协作”。

适合放入：

- Project 在 YeYing 生态中的职责边界。
- Project 内部领域模型，如项目、任务、文件、成员、权限。
- 多服务之间的高层关系图。
- 当前有效的架构说明。

不适合放入：

- 某个接口的字段协议，放到 `协议/`。
- 某个部署步骤，放到 `运维/`。
- 某个具体功能的交互和行为细节，放到 `功能/`。
- 已过时的架构背景，放到 `历史归档/`；形成正式取舍的记录放到 `决策记录/`。

### 协议

放稳定协议和跨系统契约，回答“双方按什么字段、流程、状态码、签名和版本协作”。

适合放入：

- 登录协议、身份凭证协议、访问令牌协议。
- 应用运行时协议。
- 持久化存储协议。
- 文件内容存储协议。
- API 参数、返回结构、错误码、版本兼容策略。

协议文档必须写清：

- 协议版本。
- 参与方。
- 请求和响应结构。
- 错误码或失败原因。
- 安全边界。
- 兼容策略或明确“不兼容旧协议”。
- 升级步骤。

### 功能

放用户可见功能的产品和实现说明，回答“用户怎么用、系统怎么响应、代码大致如何实现”。

适合放入：

- 文件预览和编辑。
- 项目、任务、评论、通知、权限等模块功能。
- 登录入口、身份绑定、用户资料等业务流程。
- 页面状态、按钮行为、权限表现。

功能文档应尽量按模块建子目录，例如 `功能/文件/Office预览编辑.md`。如果一个功能跨多个模块，应放在主责任模块下，并在文档内列出影响模块。

### 集成

放 Project 与外部或生态服务的集成文档，回答“Project 怎么接入这个服务、需要哪些配置、服务边界在哪里”。

适合放入：

- Node Registry 接入。
- Agent Runtime 接入。
- Wallet 和通行证接入。
- OnlyOffice 部署和 Project 配置。
- PlantUML Server、S3、Drawio 等第三方或生态组件。

如果文档重点是协议字段，放 `协议/`；如果重点是某个外部服务的接入配置，放 `集成/<服务>/`；如果重点是生产部署和故障处理，放 `运维/`；如果重点是用户功能，放 `功能/`。

### 运维

放运维执行手册和生产 runbook，回答“生产上怎么执行、怎么验证、怎么回滚”。

适合放入：

- 部署手册。
- 生产升级手册。
- 数据迁移手册。
- 备份恢复手册。
- 故障处理步骤。

运维文档必须包含：

- 前置条件。
- 配置项。
- 执行步骤。
- 验证清单。
- 回滚或降级方案。
- 风险和注意事项。

### 开发

放开发者辅助文档和生成式文档，回答“本地开发、调试、生成、排查该怎么做”。

适合放入：

- API URL 和控制器方法映射。
- 前端事件总线映射。
- 本地调试说明。
- 编码约定和脚本说明。
- 由命令生成的开发辅助文件。

生成式文档必须在文件开头标明生成命令，避免手改后被覆盖。

### 决策记录

放架构决策记录，回答“为什么做这个选择，当时有哪些备选方案，最终决定是什么”。

适合放入：

- 跨系统职责边界决策。
- 重要技术路线选择。
- 废弃旧协议或迁移到新协议的原因。
- 与 Node、Agent、Wallet、Project 边界相关的长期选择。

决策文档应使用日期前缀，例如 `2026-08-应用运行时职责边界.md`。决策一旦被后续决策替代，不直接删除，而是标记状态并链接新决策。

### 历史归档

放历史文档、已废弃方案、背景材料，回答“以前为什么这么想、哪些内容不能再作为当前实现依据”。

适合放入：

- 已被替代的 V1/V2 架构稿。
- 历史设计。
- 已废弃的兼容方案。
- 仅用于理解演进过程的材料。

归档文档必须在开头写清：

```markdown
> 历史文档：本文仅作背景参考，不代表当前实现。
> 当前实现请参考：...
```

## 文档类型

### 当前说明

描述当前有效实现或当前推荐方案。文件开头应明确状态：

```markdown
> 状态：当前有效
> 最后验证：2026-08-31
```

### 设计草案

用于尚未落地的方案。文件开头应明确草案状态和待确认项：

```markdown
> 状态：设计草案
> 最后验证：2026-08-31
> 待确认：部署归属、接口字段、迁移窗口
```

草案不能被 README 描述成当前能力。README 链接草案时必须注明“草案”。

### 协议文档

协议文档必须版本化。推荐文件名：

```text
<domain>-<protocol>-v<major>.md
```

示例：

```text
identity-login-v1.md
app-runtime-v1.md
file-content-storage-v1.md
```

如果协议发生不兼容变更，新建 `v2` 文档；如果只是补充字段或修正文案，更新原文档并记录变更说明。

### 操作手册

操作手册面向执行，不写大段背景。推荐结构：

```markdown
# 标题

## 适用范围
## 前置条件
## 配置项
## 执行步骤
## 验证
## 回滚
## 常见问题
```

### 生成式文档

生成式文档应放在 `开发/`，并在开头保留生成来源：

```markdown
> 生成文件：是，不要手动修改。
> 生成命令：npm run events:map
> 来源脚本：scripts/gen-events-map.mjs
```

如果生成脚本当前输出到旧路径，迁移时应同步修改脚本输出路径。

### 历史文档

历史文档不能和当前有效文档同层混用。迁入 `历史归档/` 后，原位置如果需要保留入口，应只保留跳转说明，不保留完整旧内容副本。

## 命名规则

- 文件名优先使用中文；协议文件也使用中文，仅保留 `v1`、`v2` 等版本标识。
- 同一类文档保持一致风格，不混用 `V1`、`v1`、`版本1`。
- 协议文件统一使用小写 `v1`、`v2`。
- 操作手册统一使用“主题+手册.md”，例如 `生产升级手册.md`、`S3迁移手册.md`。
- 历史文档迁入 `历史归档/` 后，文件名可以保留原名，但 README 中必须标注历史状态。
- 不使用“新方案”“最终版”“临时”“整理版”等无法长期维护的名字。

## 状态标识

建议每份非生成式文档在正文开头加状态块：

```markdown
> 状态：当前有效 | 设计草案 | 历史文档 | 已废弃
> 最后验证：YYYY-MM-DD
> 适用版本：可选
```

状态含义：

- `当前有效`：可以作为开发、部署或排障依据。
- `设计草案`：还没有完全落地，不能作为生产执行依据。
- `历史文档`：只保留背景价值。
- `已废弃`：明确不再使用，必须链接替代文档。

“最后验证”表示内容已经与代码、配置或生产流程核对，不等同于 Git 的最后修改时间；没有实际核对时不要随意更新该日期。

## README 维护规则

`docs/README.md` 是根导航；各顶层目录下的 `README.md` 是局部索引，不能替代根导航。后续维护按以下规则执行：

- 新增文档必须同步加入 README 或对应子目录 README。
- README 中每个链接必须写一句用途说明。
- README 不复制正文内容，只说明“读哪个文档解决什么问题”。
- 当前有效文档排在历史文档前。
- 草案和历史文档必须在链接说明中显式标注状态。
- 如果一个目录文档超过 8 个，或已经存在多个稳定子主题，必须新增或更新该目录下的 `README.md` 做局部索引。

## 图表规则

系统关系、调用链、部署拓扑、状态机优先使用 PlantUML，便于在 Markdown 中稳定维护。

推荐图类型：

- 系统关系：`component` 或 `deployment`。
- 调用流程：`sequence`。
- 状态流转：`state`。
- 数据结构关系：`class` 或 `entity`。

PlantUML 图应和正文放在同一文档中，除非多个文档复用同一张图。图只描述关键关系，不把所有字段和异常路径塞进同一张图。

## 跨系统文档组织

Project 涉及 Node、Agent、Wallet、OnlyOffice 等系统时，按主责任方决定落位：

- Project 自身业务边界：`架构/`。
- Project 与外部系统的接口契约：`协议/`。
- Project 接入某个服务的配置和依赖：`集成/<服务>/`。
- 生产部署和故障处理：`运维/`。
- 用户可见功能：`功能/<模块>/`。
- 为什么选择这种关系：`决策记录/`。

例如 OnlyOffice 相关文档可以拆为：

- `功能/文件/Office预览编辑.md`：用户如何预览和编辑 Office 文件。
- `集成/OnlyOffice/Project配置.md`：Project 如何配置 OnlyOffice 地址、JWT、回调和内网访问。
- `运维/OnlyOffice部署手册.md`：生产如何部署、验证和回滚。
- `协议/Office文档会话协议-v1.md`：如果后续抽象自有文档会话协议，再放协议字段。

## 与 ai-kb 的关系

`docs/` 是工程和架构文档，面向开发者、维护者和部署者。`resources/ai-kb/` 是产品内 AI 助手检索知识库，面向用户问答和功能解释。

当文档改动涉及用户可见能力时，需要同步判断是否更新 `resources/ai-kb/`：

- 菜单、按钮、页面流程变化：需要同步。
- API 参数、错误码、权限行为变化：需要同步。
- 纯内部目录规划、历史归档、开发者维护规则：通常不需要同步。

本文档属于内部文档治理，不改变用户可见能力，因此不需要同步 ai-kb。

## 新文档落位流程

新增文档前按以下顺序判断：

1. 这是当前能力、草案、协议、操作手册、生成物，还是历史背景？
2. 文档主问题是架构、协议、功能、集成、运维、开发辅助，还是决策？
3. 是否需要版本号？
4. 是否需要 PlantUML 图？
5. 是否需要同步 README 或子目录 README？
6. 是否涉及用户可见行为，从而需要同步 ai-kb？

建议最小模板：

```markdown
# 文档标题

> 状态：当前有效
> 最后验证：YYYY-MM-DD

## 背景
## 范围
## 方案
## 配置或接口
## 验证
## 后续演进
```

## 迁移策略

现有 `docs/` 暂不强制迁移。后续按以下策略逐步收敛：

- 新增文档直接放入目标目录。
- 修改旧文档超过正文三分之一时，顺手迁移到目标目录。
- 多个旧文档内容重叠时，合并成一个当前有效文档，其余迁入 `历史归档/`。
- V1/V2/V3 这类演进稿，如果不再代表当前实现，迁入 `历史归档/` 并在 README 标注历史状态。
- 生成式文档迁移时，同步修改生成脚本输出路径。
- 每次迁移只处理一个主题，避免大规模移动导致 review 困难。

## 当前阶段建议

当前阶段先执行三件事：

1. 保留现有 `docs/` 文件位置，不做批量移动。
2. 从下一份新文档开始使用本规划的目录结构和状态标识。
3. 等 OnlyOffice、应用运行时、登录协议等文档继续稳定后，再按主题迁移到 `功能/`、`集成/`、`协议/` 和 `决策记录/`。
